OmniReach: how it actually works

A white-label outbound voice-agent platform. One ElevenLabs agent is re-skinned per call into any company, any industry, any of 204 markets and 74 languages, without creating a new agent each time. This document explains every layer, with the real code.

1. What it is, in one breath

OmniReach places outbound phone calls that are handled by an AI voice agent. You upload or connect a list of customers, choose what the call is about (a payment reminder, an appointment confirmation, a renewal), and the system dials each person, holds a real conversation, takes actions during that conversation (books a callback, logs a promise to pay, flags a dispute), and writes the outcome back into your system of record.

The part that makes it a product rather than a script: the same deployment serves any company. Choose an industry and a country, and the console composes a complete agent (brand name, agent name, currency, honorific style, compliance framework, language, voice, conversation playbook) and runs it. Change two dropdowns and it is a different company in a different market.

The one-sentence version for a prospect: "It is a multi-tenant outbound calling platform where the AI agent is assembled per call from a company profile, so one deployment can run demos or campaigns for any client, in any market, without touching code."

2. The stack, and why each piece is there

Language and runtime

JavaScript on Node.js, CommonJS modules, throughout. One language across backend and frontend, so there is no context switching and no serialisation layer between two ecosystems.

Notably absent: no ORM, no auth library, no JWT library, no chart library, no frontend framework. Each of those was a deliberate decision, covered below.

Frontend

A single HTML file. Vanilla JavaScript. No framework, no build step, no bundler.

  • Why: the whole console is one file that the Node server hands out. Nothing to compile, nothing to deploy separately, no build that can break on someone else's machine. Handing the project to the US sales team meant zipping a folder, not explaining a toolchain.
  • The trade-off, stated honestly: at roughly 3,000 lines it is at the top end of what one file should hold. A larger product would want a component framework. For a single-purpose console it is the right call, and it removed an entire category of operational problems.

Charts and audio

Analytics bars are pure CSS with inline widths. Audio playback uses the browser's built-in <audio> and new Audio(). No chart library, no audio library. That keeps the page dependency-free and avoids Content Security Policy problems in restricted environments.

Three things to notice, because they are the questions people ask:

  1. The browser never speaks to ElevenLabs. Not once. Every byte goes through our backend.
  2. The same Node process serves the console and the API. express.static serves the HTML, so there is one command, one port, one origin, and no CORS in production.
  3. Traffic goes both ways. We call ElevenLabs to start calls and read results; ElevenLabs calls us during a conversation when the agent wants to do something.

4. The single most important design decision

The obvious way to build this is: a client wants a demo, so create an ElevenLabs agent for them. Ten clients, ten agents.

We do not do that. There is one ElevenLabs agent, and every call re-skins it on the fly.

How one agent becomes any company

ElevenLabs lets a call carry a conversation_config_override: a block that replaces parts of the agent's configuration for that conversation only. We send, per call:

  • the entire system prompt (assembled fresh from the company profile and the use case)
  • the LLM to think with
  • the language
  • the first message the agent speaks
  • the voice id, and optionally stability, speed and similarity

Plus dynamic_variables: the flattened company profile and this customer's data, which fill the {{placeholders}} inside the prompt.

Why this is the right call, and how to defend it

  • No agent sprawl. Fifty prospects do not become fifty agents to keep in sync. Change the prompt once and every future call uses it.
  • No account limits. Agents are a metered resource. Calls are not.
  • It is ElevenLabs' own recommended multi-tenant pattern, not a workaround.
  • Isolation is per conversation. Two calls happening at the same instant with completely different prompts, voices and languages do not interfere, because the override travels with the conversation, not with the agent. This is the direct answer to "what if two people demo at once".
The gotcha that cost real time, worth telling as a story: overrides must be enabled on the agent's Security tab and published. Toggling them in a draft branch does nothing. Our first live call failed with Override for field 'stability' is not allowed by config, then failed again on a different field, then again, because ElevenLabs rejects the first disallowed field and stops. Peeling an onion. The fix was not just to publish, but to stop guessing entirely, which is section 7.

5. How ElevenLabs data reaches the front end

The rule is absolute: the browser calls our API, our API calls ElevenLabs. Three reasons, and you should give all three because each answers a different questioner:

  1. Security. The API key would be readable by anyone pressing F12. It lives only in web/backend/.env on the server. There are zero occurrences of sk_ anywhere in the frontend file.
  2. CORS. ElevenLabs' API does not permit direct browser calls anyway.
  3. Normalisation. Workspace voices and library voices come back in two different shapes. The backend flattens both into one, so the UI renders a single kind of row.

Two details worth knowing, because they look like bugs

Recordings and the <audio> tag. An <audio src="..."> element cannot send an Authorization header. So for recordings only, the session token travels as a query parameter and the auth gate accepts it there: /api/call/abc/audio?token=.... The ownership check still runs, so one partner cannot fetch another's recording.

Voice previews are the one direct-to-browser exception. ElevenLabs' preview_url is a plain public MP3 on Google Cloud Storage with access-control-allow-origin: *. No key is needed, so the browser plays it directly. Proxying it would burn our bandwidth for no benefit.

ElevenLabs answers with a conversation_id. We store it against our own call record, and that id is the thread we pull on for everything afterwards: status, transcript, recording, and matching up the tool webhooks the agent fires mid-conversation.

Say this clearly if asked "so where does the AI actually run?" The LLM and the speech both run inside ElevenLabs. We do not stream audio, we do not run a model, we do not hold the call. We compose the instructions, hand them over, and then observe and record. That is why the system is cheap to run and why a laptop can host it.

Where the pieces come from

  • dynamic_variables = the company profile flattened to a flat key/value map, merged with this customer's row from the CSV or CRM. Everything is stringified, because ElevenLabs expects strings.
  • prompt = assembled by assemblePrompt(), section 9.
  • first_message = built from the localised opener catalogue, in the customer's language.
  • voice_id = whatever the profile carries, chosen by hand or auto-matched to the market.

7. How overrides are made safe

An override is only accepted if the agent has that specific field enabled. Send a field that is not allowed and the whole call is rejected. Early on this made setup fragile, because the person configuring the agent had to tick exactly the right boxes and publish.

The fix: stop guessing. Ask the agent what it permits, then send only that.

// voice-providers.js — read what the agent allows, cache for 2 minutes
async function fetchAllowedOverrides(e) {
  const c = _allowedCache[e.agentId];
  if (c && (Date.now() - c.ts) < 120000) return c.data;
  const r = await fetch(`.../v1/convai/agents/${e.agentId}`, { headers: { 'xi-api-key': e.apiKey } });
  const d = await r.json();
  const data = ((d.platform_settings || {}).overrides || {}).conversation_config_override || null;
  _allowedCache[e.agentId] = { data, ts: Date.now() };
  return data;
}

// then every field is gated before it is added to the payload
const ok = (path, dflt) => allowed ? digBool(allowed, path) : dflt;
if (prompt   && ok('agent.prompt.prompt', true))  ap.prompt = prompt;
if (voice.voice_id && ok('tts.voice_id', true)) tts.voice_id = voice.voice_id;
if (isNum(voice.stability) && ok('tts.stability', false)) tts.stability = voice.stability;
The outcome, and it is a good line to use: "Override not allowed" errors are now impossible on any agent. If the agent permits voice tuning, we send it. If it does not, we quietly drop those fields and the call still goes through with the prompt, voice and language. The system adapts to the account rather than demanding the account be configured a particular way.

The one thing that cannot be overridden

The TTS engine (Flash v2.5, Multilingual v2, v3) is set on the agent and has no per-call override. This matters because engines differ in language coverage: Flash speaks 32 languages, v3 speaks 74. Selecting Slovenian on a Flash agent would produce a call in the wrong language, silently. So the console reads the agent's real engine and says so:

  • green tick when the agent's engine covers the chosen language
  • a red block naming the actual engine when it does not, with instructions
  • the language dropdown itself marks entries as · v3 only

8. The agent calling back into us: actions

A conversation that only talks is a demo. A conversation that does something is a product.

We register 14 webhook tools on the ElevenLabs agent, each pointing at {PUBLIC_BASE}/api/agent-tool/{name}. Mid-conversation the agent decides to call one, and ElevenLabs makes an HTTP POST to our server.

A real bug worth telling: calls were never ending on their own. The prompt said to end the call, but end_call was switched off on the agent, so it physically could not hang up. Every call ran to the ten-minute cap. Diagnosed by reading the agent config over the API, not by staring at the prompt. Lesson: when behaviour contradicts the instructions, check whether the capability exists at all.

How a webhook finds its call

ElevenLabs sends the conversation id in a header. We look up our call record by it, append the outcome to a timeline, and if that user has write-back enabled, push it to their CRM immediately.

const convId = req.get('elevenlabs-conversation-id') || params.system__conversation_id || '';
const entry  = findCallEntry(convId);
// the webhook has no user session, so write-back keys off the CALL's owner
const cfg = getWriteback(entry.userId);

That last line matters: the webhook arrives from ElevenLabs with no logged-in user, so it must determine whose data this is from the call record itself. Getting that wrong would push one partner's outcomes into another partner's CRM.

9. The prompt engine

The prompt is not a template with holes. It is assembled per call from layers.

function assemblePrompt(useCase, profile) {
  const arch = resolveArchetype(useCase, profile);        // which of the 9 shapes is this?
  const parts = [
    readPrompt('global_prompt.txt'),                     // 1. how to behave on ANY call
    readPrompt(USE_CASE_FILES[arch]),                     // 2. the shape of THIS kind of call
  ];
  if (uc.playbook) parts.push('## THIS SPECIFIC CALL ...' + uc.playbook);  // 3. this client's specifics
  if (t) parts.push('## WHEN TO END THIS CALL' + t);      // 4. the end-call rule
  return parts.join(sep);
}

The 9 archetypes

This is the idea that makes 666 use cases manageable. A call's shape is separate from its subject. Chasing an overdue invoice in banking and chasing one in logistics are the same conversation with different nouns. So there are nine conversation shapes:

payment_reminder, overdue_followup, sales_offer, appointment_reminder, feedback_survey, lead_qualification, renewal_retention, service_notification, document_collection.

Each has a node file and an end-call transition file: 19 prompt files, about 1,600 lines of authored conversational instruction.

Two layers appended at call time

  • Audio tags (when enabled). Emotive cues like [warmly], [chuckles], [serious]. Critically, there is a palette per archetype: an arrears call is forbidden from ever using [laughs] or [smiling], because sounding cheerful while chasing a debt is the worst sound the agent could make. A sales call permits light warmth.
  • Demo realism (on by default, meant to be off in production). A real receptionist knows which doctor is in on Thursday. An agent that says "I have no information about that" reads as broken. So it invents small everyday operational details, region-appropriate, and holds them consistently if challenged. With a hard carve-out: never invent anything financially binding, medical, legal, or already supplied in the call data.

The assembled prompt is roughly 43,000 characters, about 11,000 tokens, per call. That is a deliberate trade: it costs more per call and adds first-token latency, and it buys an agent that holds up when a prospect actively tries to break it.

Pick a country, and the console picks a voice. The scoring is deliberately ordered, because the failure modes are not equal.

A bug worth telling, because it shows the value of measuring: one Hindi voice was being auto-selected for 38 of 79 markets, including Japan, Germany and Brazil. Two causes compounded: most non-English markets were configured with the accent "standard", meaning "no particular accent needed", but that voice's accent label was literally standard, so it scored a perfect accent match. And the language guard compared language names against data that held only language codes, so it never fired once. Rewriting the scorer to put language first took Hindi voices from 38 foreign markets to zero, across all 204.

12. Two people using it at once

This is the question you flagged, and it has two halves that are worth separating because people conflate them.

Half one: the ElevenLabs side is safe by construction

Because the configuration travels with the conversation rather than living on the agent, two simultaneous calls cannot interfere. Partner A's call carries A's prompt, A's voice, A's language. Partner B's carries B's. The shared agent holds no per-call state. Nothing needed fixing here.

Half two: our own server had genuinely shared state, and that did need fixing

The original build had a single global activeProfile. Two people building different companies would overwrite each other. That is a real bug and it was fixed by making every piece of mutable state per-user.

// server.js — the concurrency fix, stated plainly in the code
let callHistory = [];              // every entry stamped with userId
let userCampaigns = {};            // { userId: campaign } — partners' campaigns never collide
let activeProfile = null;          // the DEFAULT only: a seed for new users
let userProfiles = {};             // { userId: profile } — this is the concurrency fix
let userWritebackConfigs = {};      // { userId: {...} } — each partner keeps their own

// and every request resolves through the user, never the global
function getProfile(req) { return userProfiles[req.user.id] || activeProfile; }
function visibleCalls(req) {
  return req.user.role === 'admin' ? callHistory : callHistory.filter(c => c.userId === req.user.id);
}

What is isolated per user

  • the active company profile (the whole agent configuration)
  • call history, transcripts and recordings
  • analytics
  • write-back / CRM destination
  • bulk campaign progress
  • saved bookmarks and schedules

Settings and credentials are admin-only outright: partners cannot see or change the ElevenLabs configuration, and the nav items are hidden for them.

Three concurrency bugs that were found by testing, not by reading

  1. The campaign closure. A bulk campaign's async loop read the global campaign variable, so one partner stopping their campaign stopped everyone's. Fixed by capturing a local reference: const camp = ... inside the closure.
  2. The Sync button. POST /api/history/sync read and returned the global call history, so any partner pressing Refresh received every other tenant's calls. This was the one place the isolation work had missed, and it was found while fixing something else.
  3. The batch replace that missed one. A find-and-replace across the file updated every stampUser call except the simulate handler, because that line had a different suffix. Caught by a test that placed a call as a partner and checked the admin could see it.

How it was verified: a second server instance on a different port with its own data directory, two accounts signed in simultaneously, each configuring a different company and running a campaign. Then assertions: A sees only A's calls, B cannot reach A's recording (403), A's stop does not stop B, the two campaigns keep distinct counts, and the admin sees both. Twenty-eight of these checks in the signup and isolation suite alone.

13. Authentication, built from scratch

No Passport, no Auth0, no jsonwebtoken. Node's built-in crypto module does both jobs in 83 lines.

// passwords: scrypt, which is deliberately slow and memory-hard
const salt = crypto.randomBytes(16).toString('hex');
const hash = crypto.scryptSync(pw, salt, 64).toString('hex');
return `scrypt$${salt}$${hash}`;                    // algorithm stored with the hash, so it can be migrated

// tokens: payload + HMAC-SHA256 signature, the same shape as a JWT without the library
const p   = Buffer.from(JSON.stringify(body)).toString('base64url');
const sig = crypto.createHmac('sha256', secret()).update(p).digest('base64url');
return `${p}.${sig}`;

// verification compares in constant time, so the signature cannot be guessed byte by byte
crypto.timingSafeEqual(Buffer.from(sig), Buffer.from(expected));

Why hand-rolled: the requirement was a single self-contained deployment with no external identity provider and no database dependency. A dependency here would have added a service to run, or a library whose CVEs we would have to track, for a login screen. Both scrypt and HMAC-SHA256 are standard primitives used correctly, including the constant-time comparison that hand-rolled auth usually gets wrong.

Account creation

Three routes, chosen because a partner-facing platform cannot require an admin for every signup:

  • admin creates the account directly
  • self-signup from a pre-whitelisted company domain, auto-approved with a conservative daily cap
  • self-signup from anywhere else, which lands in an approval queue

Every account created by any route carries mustChangePassword, and the console forces the change before anything else is usable.

Be ready to say this, because a sharp questioner will ask: an email domain is not proof of identity. There is no mailbox verification, so domain auto-approval gets the reduced quota rather than full trust. Real email verification is the clean fix and it is a known gap, not an oversight.

14. Persistence: two backends, one interface

store.js exposes one set of functions. Behind them:

  • Postgres when DATABASE_URL is set (managed: Neon, Supabase, Railway, RDS)
  • JSON files when it is not, so the thing runs on a laptop with zero setup

The application shape did not change: everything loads into memory once at boot, and every mutation calls saveHistory() or similar. That meant swapping storage engines touched no call sites.

Writes are debounced and serialised

A 200-call bulk campaign would otherwise issue 200 database writes. Writes are debounced by 300 ms and serialised per table, so the same campaign produces roughly one write. Inserts are chunked against a 60,000-parameter budget, and a SIGTERM handler flushes pending writes so a deploy does not lose the last few seconds.

Seven tables: users, calls, user_profiles, user_writeback, settings, schedules, bookmarks. Volatile shapes live in JSONB; fields that are filtered on (user id, timestamp, simulated) are promoted to real columns with indexes.

The reason Postgres matters, and it is not performance: container filesystems are ephemeral. On Render, Railway or Fly, a redeploy wipes data/. Without a database, every account and every call record disappears on the next deploy. That is the argument, not throughput.

15. Getting data in, and pushing outcomes back out

In: sources

CSV upload, a URL returning CSV or JSON, a published Google Sheet, or a REST endpoint with headers and a JSON path. Salesforce, HubSpot, Zoho and Postgres connectors are interface-ready stubs that fail with a helpful message rather than pretending.

The smart queue

Rows are not dialled in file order. Each row is analysed and:

  • routed to the most appropriate enabled use case based on the columns present (an amount_overdue column implies collections, appointment_date implies a reminder)
  • ordered by urgency: overdue before payment reminder before appointment before renewal
  • skipped with a stated reason: missing phone number, previously marked do-not-call, or a duplicate number already in the batch

Out: write-back

Outcomes push to an in-app preview, a webhook, or an enriched CSV download, with a configurable field mapping of 14 outcome fields. And it can fire automatically the moment record_call_outcome arrives, which makes a very good demo: enable it, run a call, and the row appears in the CRM view while the call is still ending.

16. Simulation mode

A toggle in the header. With it on, calls are fully simulated: a realistic transcript is generated for the chosen use case using the active profile's own values, a plausible outcome is picked from weighted branches (including voicemail and wrong-person), and the same action tools fire.

So history, transcripts, outcome chips, analytics and CRM write-back all populate exactly as they would on a real call, with no credentials, no phone number and no cost. Every simulated call is flagged so it can never be mistaken for a real one, and simulated calls are excluded from quota counting.

Why this is worth highlighting: it means the platform can be demonstrated end to end on a laptop with no Twilio number and no spend, and it means the sales team can rehearse without dialling a real person. It also made the whole system testable without placing calls.

17. Analytics, and a bug worth admitting

Analytics originally reported a 0% connect rate on 26 real calls, one of which was a 74-second answered conversation.

The cause: connect rate keyed entirely off disposition, which only exists if the agent called record_call_outcome. Real calls frequently do not have it. So genuinely connected calls were being counted as failures.

function classifyCall(c) {
  if (c.status === 'failed' || cs === 'error')        return 'failed';
  if (disp === 'no_answer_voicemail' || disp === 'wrong_person') return 'noReach';
  if (disp)                                          return 'connected';
  if (c.callSuccessful === true)                   return 'connected';
  if (cs === 'ended') return dur >= 10000 ? 'connected' : 'noReach';
  return 'pending';   // placed, outcome not synced yet
}
// pending is EXCLUDED from the denominator, so un-synced calls do not drag the rate down
connectRate = resolved ? Math.round(connected / resolved * 100) : 0;

The fourth bucket, pending, is the important idea: a call that has been placed but whose outcome has not come back yet is not a failure, and counting it as one is how you get a 0%.

18. Scheduler

Schedules run agents on a recurrence: once, daily, weekly, monthly. The timing engine is separate and pure, which makes it testable without a clock.

  • Timezones use Intl.DateTimeFormat rather than manual offset arithmetic, so daylight saving is handled by the platform, not by us.
  • Each firing writes a slot key, so a restart or a slow tick cannot fire the same slot twice.
  • A calling-window guard prevents dialling outside permitted hours.
  • The tick runs every 30 seconds: fine enough for minute-accurate slots, cheap enough to ignore.
Deployment consequence worth knowing: every running instance ticks its own scheduler against whatever store it is pointed at. If five laptops shared one database, one daily schedule would fire five times. That is exactly why the handover package ships with DATABASE_URL blanked, so each local install keeps its own data.

20. Running and handing it over

One command, one port: node server.js serves the console and the API together on 3002.

For the US sales team there are three numbered batch files: 1-SETUP.bat (checks Node, installs, prepares settings), 2-START.bat (starts it, waits for the port, opens the browser), 3-STOP.bat (stops by port, not by killing every Node process). Anticipated questions, with answers

Why not build the voice agent yourselves instead of using ElevenLabs?

Because the hard part of a voice agent is not the orchestration, it is sub-second speech and interruption handling on a real phone line. ElevenLabs solves that. Our value is everything around it: the per-call agent composition, the market catalogues, the conversation design, the actions, the isolation and the write-back. And the provider layer is an adapter, so Retell is already a supported fallback and a third provider would be one file.

What happens if two demos run at the same moment?

Nothing. The configuration travels with the conversation, not with the agent, so ElevenLabs keeps the two calls entirely separate. On our side every piece of mutable state is keyed by user id, so two people building different companies never see each other's work. We tested this explicitly with two accounts running campaigns simultaneously.

Is the API key safe?

It never leaves the server. The browser only ever talks to our own API. We verified there are zero occurrences of the key prefix anywhere in the frontend file, and the masked preview shown in Settings is admin-only.

How do you support 666 use cases without 666 prompts?

A call's shape is separate from its subject. There are nine conversation shapes, and a use case supplies a playbook layered on top of one of them. Chasing an overdue invoice is the same conversation in banking and in logistics, with different nouns.

Why one HTML file with no framework?

Because the deliverable is a folder someone can run. No build step means nothing to compile, nothing to deploy separately, and no toolchain to explain when handing it to a sales team. At this size it is the right trade. If the console grew substantially I would move to a component framework, and I would say so.

Why write your own authentication?

The requirement was a self-contained deployment with no external identity provider and no mandatory database. Adding a library for a login screen would have meant a service to run or CVEs to track. scrypt and HMAC-SHA256 are standard primitives, used correctly, including the constant-time comparison that hand-rolled auth usually gets wrong. If this went to enterprise scale I would move to SSO, and the abstraction is already there: the user store sits behind six functions.

How do you know it works? What did you test?

Every change was verified on an isolated second instance with its own data directory and credentials that physically could not place a call, with the production data snapshotted and hash-compared afterwards. The suites run in the hundreds of assertions: multi-tenant isolation, guardrails, signup and approval, the Postgres round-trip, the password flow, prompt structure, the voice matcher across all 204 markets, and the batch files run end to end from a clean unzip. Several real bugs were found this way, including the cross-tenant leak in the Sync button.

What does a call cost?

Three components: ElevenLabs conversational minutes, the LLM tokens, and Twilio telephony. Our prompt is deliberately large, around 11,000 tokens per call, which is a real cost worth being honest about. It buys an agent that does not fall apart when someone tries to break it. Simulation mode costs nothing at all, which is how demos and rehearsals should be run.

Can it scale?

The call path scales with ElevenLabs, since we do not hold the audio. Our server is stateless per request apart from in-memory caches, and moving to Postgres makes it horizontally scalable, with one caveat I would raise unprompted: the scheduler ticks per instance, so running multiple instances would need a leader election or a database lock before it is safe.

What is the biggest risk?

Provider dependency. If ElevenLabs changes its API or pricing, we are exposed. That is mitigated by the adapter pattern, and Retell is already wired as a fallback. Second is prompt drift: a large authored prompt needs review discipline, which is why the end-call rules and the audio-tag palettes are separate files with their own structural checks.

Honest limitations, and why saying them helps

Volunteering these makes the rest of the answers more credible, and every one of them has a next step.

  • No email verification on signup. Domain matching is a heuristic, which is why auto-approved accounts get a reduced quota. Next step: a verification email.
  • The scheduler is single-instance. Safe as deployed, needs a lock before scaling out.
  • Prompt cost. Roughly 11,000 tokens per call is deliberate but not free. It could be trimmed by loading the demo-realism and audio-tag layers only when they are actually enabled.
  • Not yet deployed. It runs on a laptop and is ready for a host: HTTPS, secrets in environment variables, trust proxy, and the Postgres migration, which is written and tested.
  • Twilio geo-permissions. International destinations must be enabled per country in the Twilio console. A Botswana call failed for exactly this reason, and it is a configuration step, not a code fix.
If you remember four things, remember these:
1. One agent, re-skinned per call by conversation_config_override. That is the architecture.
2. The browser never touches ElevenLabs. The key lives only on the server.
3. Concurrency is safe on both sides: per conversation at ElevenLabs, per user id in our state.
4. Nine conversation shapes times 666 subjects is why it covers so much ground without 666 prompts.
